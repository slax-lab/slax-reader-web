# Prompt 模板指南

`codex review` 的效果取决于你给的审查维度。本目录 `prompts/` 下有几份现成模板，按文档类型挑一份传给脚本第二参数（Mode B），或在 Claude 驱动模式（Mode A）里直接把内容拼进 codex 的 prompt。

**规则**：每份模板结尾都必须有「如果没有问题，明确回复"通过"」——这是循环自动终止的信号。

---

## 现成模板

| 模板文件 | 适用文档类型 | 审查维度概要 |
| --- | --- | --- |
| `prompts/test-spec.txt` | 测试方案 / 用例设计 spec（脚本内置默认，不传第二参数即用它） | 用例预期 vs 源码真实行为、mock 链路假阳性、用例数对账、范式一致性 |
| `prompts/arch-feature.txt` | 功能实现方案 / 架构方案（非测试） | 文件操作正确性、Nuxt 层兼容性、流程完整性、SSR/CSR、边界、实施顺序风险 |
| `prompts/ui-frontend-example.txt` | 前端 UI/布局实现方案 | 源码结构匹配、层 alias 覆盖、Vue 多根/hydration、事件/拖拽泄漏、z-index/布局、与 design demo 一致性。**这是一份高度具体的真实样例**，照它的粒度为你的 UI 方案改写。 |

---

## 怎么选 / 怎么写自定义模板

1. **测试 spec** → 直接跑（内置默认）。
2. **功能/架构方案** → 传 `arch-feature.txt`。
3. **前端 UI 方案** → 参照 `ui-frontend-example.txt` 的粒度，针对你的具体页面/组件改写一份（照抄不改会跑偏，因为它绑定了特定文件名/token）。
4. **其它文档**（如 API 契约、数据迁移方案）→ 现写一份，套路：
   - 开头：`审查 SPEC_PATH 中的 <文档类型>。请按以下维度找问题：`
   - 中间：3-8 条**可核对**的维度（越具体越好：点名要对账的文件、字段、分支、计数、与哪个现有范式对齐）
   - 结尾：`如果没有问题，明确回复"通过"。`

写好的自定义模板可以放在本目录 `prompts/` 下复用，或临时放任意路径传给脚本第二参数。

---

## 好维度 vs 差维度

| 差（太泛，codex 会敷衍） | 好（可核对，codex 能挖出真问题）                                                       |
| ------------------------ | -------------------------------------------------------------------------------------- |
| "看看有没有问题"         | "用例预期的字段名/分支顺序/错误文本是否与被测源码一致"                                 |
| "架构合理吗"             | "方案删除/新增的文件路径是否与源码实际结构匹配，有无遗漏引用了被删组件的其它文件"      |
| "有没有 bug"             | "Nuxt 层 alias 覆盖是否让 upstream 子模块内的消费页也用上 fork 版；4 个消费页有无遗漏" |

`SPEC_PATH` 是占位符，脚本会替换成真实文档路径；自己写 prompt 时保留这个词或直接写死路径都行。
